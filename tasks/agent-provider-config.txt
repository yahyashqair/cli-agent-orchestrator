# Task: Agent-Type Provider Configuration

## Background
- UI currently offers a single provider dropdown when launching any agent via `ControlPanel`.
- MCP server + CLI logic rely on the agent profile metadata or inherited provider, so supervisor-spawned workers cannot easily pin different CLIs per agent type.
- Requirement: allow configuring a provider override per agent profile (e.g., make `developer` use "grok code"/`codex_cli` while supervisor stays on another provider) via the UI, with safe defaults.

## Goals (Phase 1 – completed)
1. Persist a per-agent-profile provider preference (defaults to `DEFAULT_PROVIDER` when unset) that both the API/MCP tooling and UI can read/write.
2. Allow users to manage those preferences from the UI (no manual file edits).
3. Ensure terminal creation logic (especially `_create_terminal` in `mcp_server/server.py`) honors the override before falling back to the profile’s metadata or inherited provider.

## Detailed Requirements

### Backend
- **Data model**: add `agent_provider_configs` table (primary key = `agent_profile`, column `provider`). Provide helper functions in `clients/database.py` plus a light migration in `init_db()`.
- **Service layer**: add `services/agent_config_service.py` (or similar) with helpers:
  - `list_provider_configs()` returning all overrides.
  - `get_provider_for_profile(agent_profile: str) -> Optional[str]`.
  - `set_provider_for_profile(agent_profile: str, provider: str)` (upsert) with validation against `constants.PROVIDERS`.
  - `clear_provider_for_profile(agent_profile: str)` to delete override.
- **API**:
  - `GET /agent-provider-configs` → list of `{agent_profile, provider}`.
  - `PUT /agent-provider-configs/{agent_profile}` with body `{provider: "codex_cli"}` to set/update.
  - `DELETE /agent-provider-configs/{agent_profile}` to remove the override (fall back to defaults).
  - Use Pydantic models for payload/response; return 404 when deleting non-existent configs?
- **Provider resolution**:
  - Update `_create_terminal` (and any other place that decides provider server-side) to check the configured override first. Expected precedence:
    `configured_provider` > `agent_profile.provider metadata` > existing inheritance/default logic.
  - When API endpoints such as `/sessions` or `/sessions/{name}/terminals` receive an explicit `provider`, keep honoring the passed value.
  - Consider exposing a helper (maybe in the new service) to encapsulate that precedence so it stays consistent if other modules need it later.

### UI
- Add API client methods under `ui/src/api/client.ts` for the new endpoints.
- Introduce a lightweight settings modal/panel (e.g., `AgentProviderSettings`) reachable from the dashboard header or Control Panel that lists every supported agent profile (`code_supervisor`, `developer`, `reviewer`, etc.) with a provider `<select>`.
  - Show defaults (fallback to `'q_cli'` when no override exists).
  - Allow saving per-profile override and provide an option to reset to default (DELETE endpoint).
  - Surface validation errors inline.
- Update `ControlPanel` so that when the user picks an agent profile, the provider dropdown auto-selects the stored override (but still allows ad-hoc changes for a single launch). Persisting a recent config should still work.
- Make sure the settings UI stays responsive (loading/saving states) and uses existing design tokens.

### Documentation
- Update `README.md` (and `ui/README.md` if needed) to mention the new Agent Provider configuration feature + how to use it.
- If there’s a better home (e.g., `docs/`), add a short section summarizing default behavior and override precedence.

## Testing & Validation
- Add unit tests covering the new service/database helpers (e.g., `test/services/test_agent_config_service_unit.py`).
- Extend `test/mcp_server/test_server_terminal_creation.py` to assert that `_create_terminal` honors a configured override.
- Cover the new FastAPI endpoints via a lightweight unit or integration test (matching existing testing patterns).
- Run `uv run pytest -v` plus formatters (`uv run black src/ test/`, `uv run isort src/ test/`, `uv run mypy src/`).
- For the UI, at minimum verify through `npm run build` (or existing check) that TypeScript compiles; optionally add a component test if there’s precedent.

## Deliverables
- Updated backend + UI code implementing the feature.
- Tests + docs updates.
- Summary of manual verification steps taken (API exercise + UI sanity checks).

# Phase 2 – Review Fixes (NEW)

## Context
Initial implementation landed, but review uncovered regressions (see `/reports/agent_provider_review.md`). We must address the issues so overrides work end-to-end.

## Required Fixes
1. **CLI launch override support**  
   - Update `cli/commands/launch.py` so provider selection follows the same precedence as the backend (`saved override > profile metadata > inherited provider (if attaching) > DEFAULT_PROVIDER`).  
   - Likely via a helper in `services/agent_config_service` or a new utility function shared with the API/MCP layers.  
   - Add unit coverage in `test/cli/test_launch.py` to confirm the CLI uses the override when the profile has one. Ensure `validate_provider_available` still runs on the resolved provider.  

2. **Control Panel fallback when no override exists**  
   - Fix `ControlPanel.tsx` to reset `provider` to `DEFAULT_PROVIDER` (or profile metadata if available) whenever the chosen agent profile has no stored override. Currently the previous provider remains selected.  
   - Add a lightweight regression test if feasible (component or hook-level) or at least document manual verification steps.  

3. **Expose working_directory on terminals for MCP inheritance**  
   - Ensure `terminal_service.get_terminal` and the FastAPI response include `working_directory`. Update the Pydantic `Terminal` model (if needed) and UI types if they rely on this payload.  
   - `_create_terminal` should then successfully inherit the directory when creating worker terminals.  
   - Extend `test/mcp_server/test_server_terminal_creation.py` to cover this scenario.  

4. **Docs/tests alignment**  
   - Update README/UI docs only after behavior matches the advertised precedence.  
   - Add/adjust tests so each entry point (CLI launch, MCP inheritance) has explicit coverage for the override chain.  

## Validation
- Re-run `uv run pytest -v -m "not integration"` plus relevant frontend build/test commands.  
- Include a short checklist of manual verifications (e.g., CLI launch picking Codex override, Control Panel switching profiles).
